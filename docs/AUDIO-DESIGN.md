# 摇奖音效：设计整合与性能优化

面向微信小游戏的程序化音效实现说明。没有外部音频文件，全部在本地合成；本文记录**当前定稿的参数、
每条设计决策的依据（含实测数字）、性能优化过程，以及调整时该改哪个数**。

对应代码：`index.html` 的 `AudioFX` 模块（单文件，无依赖），构建后同名逻辑进入
`miniprogram/src/game-logic.js`。

---

## 1. 目标与约束

| 约束 | 具体要求 |
|---|---|
| 包体 | 小游戏首包 4MB 限制，不能塞音频文件 → 全部程序化合成 |
| 内存 | 采样率用 22.05kHz 单声道，比 44.1k 立体声省 4 倍 |
| 热路径 | 摇奖主循环里**不能创建音频节点**，只能改增益 |
| 听感 | 像真机，不像合成器；不能盖住开奖信息；不能有可辨识的循环/周期 |
| 降级 | 拿不到 WebAudio 时静默降级，绝不影响开奖 |

---

## 2. 信号链与节点预算

```
事件声：BufferSource → Gain ─┐
                              ├→ master(Gain, VOL=0.07) → destination
搅拌声：BufferSource(loop)    │
        → Gain(门控) ─────────┘
```

- **常驻节点 3 个**：`master` + 搅拌的 1 源 + 1 增益。搅拌源一直挂着、`loop = true`，
  只用 `setTargetAtTime` 改门控增益——`BufferSource` 只能 `start()` 一次，真停掉就得每局重建，
  那才是热路径上的分配。
- **事件声**：每次 1 源 + 1 增益，`onended` 里立即 `disconnect()`，不依赖 GC（各实现回收时机差异很大）。
- **主循环开销**：每帧一次 `AudioFX.stir(agitMax)`；有 0.005 死区，值不变直接 return，不排事件。

## 3. 八段采样清单

采样率 22050Hz、Float32 单声道，合计 **183,234 点 / 8.31s / 716KB**。
「总线峰值」= 采样峰值 × 播放音量 × `VOL(0.07)`。

| 段 | 时长 | 采样峰值 | 播放音量 | 总线峰值 | 触发时机 | 音色构成 |
|---|---|---|---|---|---|---|
| `stir` 搅拌 | 4.00s 循环 | 0.437 | 1.05 | -29.9 dBFS | 跟随拨盘转速 0→1 淡入 | 58 颗/秒离散撞击，200Hz 高通 + 2.4kHz 低通 |
| `fall` 下落 | 1.10s | 0.950 | 0.55 | -28.7 dBFS | 闸门抽开、整批球落进腔体 | 55 颗落球（前密后疏）+ 两记落地 + 气流层 |
| `hit` 落位 | 0.55s | 0.900 | 1.30 | **-21.7 dBFS** | 每颗球入槽 | 1500Hz 撞「咔」+ 210Hz 球体 + 95Hz 重量 |
| `out` 出球 | 0.22s | 0.720 | 1.60 | **-21.9 dBFS** | 球滑出管口 | 高 Q 带通噪声 940→560Hz 下滑（一声「嘟」） |
| `clunk` 开局 | 0.45s | 0.900 | 0.85 | -25.4 dBFS | 点「开始摇奖」 | 电磁阀闷响 + 金属壳「啪」+ 电机咬合 |
| `slide` 开阀 | 0.42s | 0.850 | 0.62 | -28.6 dBFS | 闸门沿导轨滑动 | 摩擦噪声扫频 + 起手/到位两记「嗒」 |
| `chime` 完成 | 1.15s | 0.900 | 0.62 | -28.2 dBFS | 七个号全部出完 | 三记非谐波金属铃（C5/E5/G5） |
| `tick` 复位 | 0.42s | 0.880 | 0.75 | -26.7 dBFS | 点「重置」 | 气阀泄压「噗」+ 金属件归位「嗒」 |

## 4. 六个合成基元

全部以「噪声激励 + 滤波/模态」实现，**没有一个振荡器**（`createOscillator` 调用数 = 0）。

| 基元 | 作用 | 关键参数 |
|---|---|---|
| `clickInto` | 宽带敲击脉冲，硬物相撞的主体（10~30ms） | 中心频率、Q、衰减；Q 小像「啪」，大像「嗒」 |
| `modesInto` | 物体被敲后的余振 | 非谐波比 **1 : 2.76 : 5.4 : 8.93**，每个模态 ±1.5% 抖动 |
| `thumpInto` | 重量感（球体质量、落地） | 低通噪声，无音高，所以不会变「嗡」 |
| `grainInto` | 单颗球撞球的颗粒 | 带通噪声 + 250Hz 低通重量层，尾巴取模回卷 |
| `sweepInto` | 「嘟」类带音高的短音 | 白噪声过高 Q 带通 → 窄带下滑，有音高但不发干 |
| `roomInto` | 空间感 | 4 个稀疏延时抽头 11/17/23/31ms，越晚越暗 |
| `finish` | 归一化 + 尾部淡出 | 峰值归一到目标、末尾 30~120ms 淡出，避免截断成「咔」 |

为什么不用振荡器：正弦/三角/锯齿是电子音的定义。真实硬物撞击 = 极短的宽带噪声起振 +
几个非谐波衰减模态；整数比（1:2:3）会被听成乐音。改用噪声激励后，落位声的谱峰从
**42dB / 18 根**降到 **23dB / 4 根**，主观上「电子味」消失。

## 5. 五条设计原则（都有实测依据）

### 5.1 连续感来自撞击密度，不能靠噪声床

搅拌曾经叠了一条 180~3300Hz 的带通白噪声「底床」，用来给「一直有东西在动」的质感。这是错的：

- 判据：5ms 窗 RMS 的 **p5 / 中位**（颗粒间隙还剩多少能量）。含底床 **0.73**，删掉后 **0.19**。
- 2k~6k 能量占比 19.1% → 10.3%；谱重心 1697Hz → 1346Hz。
- 听感上，那层床就是**永不间断的「沙沙」**。球本身不发声，响的只有撞击。

同样地，为了「更实」加过 80~180Hz 的低频层，结果听起来像**水声**——低频噪声就是流水。
两个错误同源：**用连续噪声去补连续性**。正确做法是提高颗粒密度（46 → 58 颗/秒）。

### 5.2 循环感的敌人是包络周期性，不是接缝

搅拌段的目标不是「好听的一段」，而是**听不出在循环**。真实搅拌是稳态的：单颗球在响，但一屋子球
同时翻，总响度几乎不变。做法三步：

1. **颗粒均匀随机铺满 4s**——写 `k/NG` 等分点会密集成拍；
2. **50ms 窗 RMS 包络压平**到中位数：增益钳 0.66~1.55，再环形平滑 4 次（相邻窗增益必须连续，
   跳变本身就是「一下一下」）；
3. **尾部 0.25s 环形折返**，接缝跳变 0.281，小于全局最大样本跳变 0.502。

达成指标：**200ms 尺度包络变异系数 0.083（max/min 1.32）**，自相关在 0.2~3.9s 延迟域的最强峰只有
0.026——即不存在任何周期成分。判断依据不是「包络有多平」，而是**有没有周期性**：起伏本身可以存在
（真实搅拌也不绝对恒定），但周期性起伏一定会被听成「隔一会儿响一下」。
曾经用 2.4s 循环 + 每 4s 起伏的版本，就是这么被听出来的。

### 5.3 先立 RMS，再软压峰值（顺序不能反）

搅拌一度「完全听不到」。探针显示链路正常（1 个常驻循环源、4.0s buffer、增益 0.847、`ctx.running`），
问题是**电平被自己压死了**：定响度时先钳峰值 0.6，RMS 只能到 0.099，总线 **-50 dBFS**。

- 持续底噪的感知门槛远高于单次瞬态。事件声 -46dBFS 听起来「合适」，对应的底噪得在 -40dBFS 上下。
- 改法：按 **RMS 0.17** 归一后走 `tanh(d·g·drive)/drive` 软饱和，峰值收敛到 0.50；
  crest 6.05 → 3.31，只削最尖的几颗，颗粒感还在。

### 5.4 混音是频谱分配问题，不是音量问题

落位声曾经「亮灯时听不到」。它不是小，而是被**掩蔽**：主体 1750Hz 正好落在搅拌能量最集中的
500–2k（占 73%）。改法两条一起上：

- 频率让位：主体降到 1500Hz，另加 **210Hz 球体实体**——0~160Hz 搅拌只剩 0.2%，这一段是落位独占的；
- 电平抬高：`place` 0.62 → 1.30。

结果落位峰值 -21.7 dBFS，比搅拌峰值高 7.2 dB。

### 5.5 每次播放都微调速率

`vary(a)` 给 `playbackRate` ±a 随机，同一段采样连续触发也不会「复读机」。
落位 ±6%、复位 ±6%、完成 ±1.5%（音高类声音不能抖太多，否则音准跑）。

## 6. 电平关系（谁压谁）

| 优先级 | 声部 | 总线峰值 | 说明 |
|---|---|---|---|
| 1 | 出球 | -21.9 dBFS | 必须跳出来，它是「有结果了」的信号 |
| 2 | 落位 | -21.7 dBFS | 与出球齐平，一局里不会互相抢 |
| 3 | 复位 / 开局 | -26.7 / -25.4 dBFS | 明确的操作反馈 |
| 4 | 下落 / 开阀 / 完成 | -28.7 / -28.6 / -28.2 dBFS | 过程提示 |
| 5 | 搅拌 | 峰值 -29.9 / RMS -39.9 dBFS | 背景底噪，全程存在 |

最坏叠加（出球 + 搅拌同刻）峰值 0.113，距削波 0.99 有充足余量；整局实测峰值 0.097。

## 7. 性能优化

### 7.1 三个独立的耗时源

原实现把「合成采样」放在首次点击里同步执行。CPU 采样后发现真正的停顿不是合成：

| 阶段 | 耗时 | 性质 |
|---|---|---|
| 合成 8 段采样 | 157ms | 纯计算（Float32Array + 滤波循环） |
| `new AudioContext()` | **186ms** | 音频线程 / 设备初始化 |
| `createBuffer` + 拷贝 | 0.4ms | 上传 |

只做「预合成」时长帧依然存在——这就是必须用 CPU 采样而不是靠猜的原因。

### 7.2 改造

1. **合成与 AudioContext 解耦**：`buildSamples` 的 `mk()` 返回纯 `Float32Array` 假 buffer，
   合成路径完全不碰 `ctx`；新增 `rawSet` 存原始数据 + `uploadSamples()` 做 createBuffer/拷贝。
   `copyToChannel` 不存在时（早期小游戏基础库）回退 `getChannelData().set()`。
2. **音频预热**：首帧之后在 `requestIdleCallback` 里跑 `prime() + ensure()`——合成和建 ctx 都不需要
   用户手势（无手势时 ctx 停在 `suspended`，点击时 `resume()`）。`resume()` 的 rejection 必须 catch，
   否则控制台每次都有未处理拒绝。
3. **节点释放**：`playBuf` / `ballFall` 的 `onended` 里 `disconnect()`。
4. **删死代码**：`mute` / `isMuted` 全项目零调用点。

### 7.3 效果

| 指标 | 改前 | 改后 |
|---|---|---|
| 点击后 >60ms 长帧 | 1 个（~200ms） | **0** |
| 点击瞬间音频工作 | build 157ms + ctx 186ms | build 0ms / upload 0.4ms |
| 加载期长帧 | — | 350ms 左右（预热，用户看入场时感知不到） |

预热代价是加载期出现一次 300ms 级长帧。若以后嫌首屏抖，把 `warmAudio` 延后即可。

## 8. 验证工具链

程序化音效不能只靠耳朵验收，仓库里留了四个工具：

| 工具 | 用途 |
|---|---|
| `_audio_render.js` | 从 `index.html` 抽取合成核心，在 Node 里离线渲染成 `_*.raw`，改动音效后**必须**重跑 |
| `_audio_spec.py` | 频谱重心/分频段占比/包络变异/谱峰突出度/自相关/接缝跳变 |
| `_e2e_audio.py` | 真实浏览器跑完整一局：在 `destination` 前插 AnalyserNode 量总线电平，按阶段统计 RMS、峰值、节点创建数 |
| `_perf_probe.py` / `_perf_scene.py` | 帧时间、长帧、draw call、场景资源清单 |
| `_diag_flow.py` | 状态机是否正常推进（rAF 计数 / 入位球数 / 阶段文本），排查「卡住不动」 |

**验收线**：整局无 JS 异常、峰值 <0.99、静默期 RMS = 0、常驻循环源恰好 1 个且时长 4.0s、
搅拌阶段 RMS 明显高于静默期、事件声数量与流程事件一一对应。

当前基线（整局 37.6s / 21 个事件）：load -57.6 dBFS、stir -42.0、draw -40.1、done -37.4，
全程峰值 0.097。

### 调试开关

- `?debug`：暴露 `window.__AFX()`（采样 peak/rms、门控增益、ctx 状态）、
  `window.__T`（合成/上传耗时）、`window.__DBG`（scene/renderer/camera）。

## 9. 调参速查

只有一个总音量入口 `VOL`，以及每段的播放音量。改完必须
`node miniprogram/build.js` 重建包。

| 症状 | 改哪里 |
|---|---|
| 整体太吵 / 太轻 | `VOL`（0.07）：它是全局乘子 |
| 搅拌听不见 | `STIR_LV`（1.05）；先确认不是被事件声掩蔽 |
| 搅拌压住出球 | 降 `STIR_LV` 或升 `ballOut` 音量（1.60） |
| 搅拌像水声 | 检查是否又加了低频层——直接删，不要调低 |
| 搅拌像沙沙 | 检查是否有连续噪声床；连续性用颗粒密度（58 颗/秒）给 |
| 听出循环/隔一会儿响一下 | 查周期成分：自相关在 0.2~3.9s 不应有峰，且不应有 LFO 调制（包络变异 8% 属正常） |
| 落位听不到 | 换频段（避开 500–2k），不是调音量 |
| 声音像电子音 | 检查是否引入了 `createOscillator`；模态比必须是非整数 |
| 点击「开始摇奖」卡一下 | 检查 `warmAudio` 是否还在跑（预热没生效就会回到 343ms） |

## 10. 小程序侧注意

- 音频上下文由 `miniprogram/adapter.js` 桥接：`GameGlobal.AudioContext = () => wx.createWebAudioContext()`，
  因此 `index.html` 里的 `new AudioContext()` 在小游戏里直接可用；`wx.createWebAudioContext`
  需基础库 ≥ 2.19.0。
- `createBuffer` 不一定接受自定义采样率：`ensure()` 里 try/catch，失败就按 `ctx.sampleRate` 重算并重传。
- `copyToChannel` 早期版本缺失，已回退 `set()`。
- 无 WebAudio 环境时 `ensure()` 返回 `null`，所有播放函数直接 return，开奖流程不受影响。
- `miniprogram/preflight.js` 会扫描代码里用到的 wx API 并提示最低基础库。

## 11. 遗留项

- **draw call 147/帧**（含阴影 pass 峰值 176）：184 个独立 Mesh、0 个 InstancedMesh、
  128 个唯一几何体（Sphere 62 / Cylinder 61 / Circle 27），三角面只有 79k——瓶颈在提交次数。
  球体共享几何 + 静态装饰合并可压到 60~80，属上手机时的工作量。
- **堆增长**：40s 会话 JSHeap +5.2MB，尚未定性是缓存还是泄漏，需要更长会话对比。
